# 用 evolutionary 压 collaboration：方向与方针

**日期**：2026-09-19 ｜ **依据**：本会话全部实测（wave42、事务债、两次"找不到"、四次自纠）

---

## 一、当前处在哪：一个单调递减的矿

**JPA 化这条线走完了。** 全仓只剩 1 处 InMemory 注入，而它跨域、需先判断是否共享内核。

回头数这条线的产出：

| 波次 | 产出 | 对 KB 的选择压力 |
| :--- | :--- | :--- |
| wave41–42 + operator | 10 个域 JPA 化 | **≈ 0**（`pressure-routing` 说的"机械执行面根本不需要 KB"） |
| 事务债 | 1 个真 bug（数据错） | **1 条新 pattern** + 2 条拦截候选 |
| 种子时机 | 1 次"找不到" | 1 行 known-gap |

**规律很清楚：机械切片对 KB 零压力，设计墙才有。**

而"设计墙"的数量是**单调递减**的 —— 项目越成熟，撞墙越少。
JPA 线已经撞完（种子时机、事务边界两个都撞过了），再往前走是**重复同类切片**。

## 二、因此方针第一条：**不要为了压 KB 而造撞墙**

具体禁止：

- ❌ 不要为了"有产出"把已经做对的东西重构一遍
- ❌ 不要为了 harvest 而放大一个不存在的设计问题
- ❌ 不要在前端零测试的情况下开大改（那不是撞墙，是拆墙）

**判据**：如果我需要**编一个**设计问题才能 harvest，那这条压力线已经枯竭 —— 该停，而不是硬跑。
（这与 `pressure-routing` 的"L1 冒充 L3"是同一条，只是换了个伪装。）

## 三、方针第二条：**下一个有真压力的目标是前端**

理由不是"它是剩下的活"，是**它同时具备三个条件**：

| 条件 | 现状 |
| :--- | :--- |
| **有决策没落地** | `topic/fe-ddd-rsc` 的决策表 2026-09-17 就写了（RSC / 服务端读模型 / BC 视图模型），仍标「待实施」 |
| **有 KB 依据** | `patterns/frontend-ddd-rsc` 条目在，且账本里有它拦过一次的记录 |
| **会撞新墙** | 前后端边界、RSC 的序列化边界、服务端状态 vs UI 瞬态 —— **和 JPA 线完全不同类的墙** |

**但它的前置条件没满足：前端零测试 = 没有基线。**

所以顺序是：

```
1. 先给前端建一条能跑的验收（哪怕只有 next build + 一条冒烟）
2. 再按决策表改造，每步有基线可验
3. 改造中撞到的墙 → 才是真的 L2→L3 压力
```

**跳过第 1 步就是重演"红着基线派双路"** —— 那正是本会话花了大力气修掉的坑
（`3ceda84` 每个 context 独立 H2）。

## 四、方针第三条：把"找基线"本身当压力源

这是本会话最有价值的一条副产品，**它值得被压出来第二次**：

> 本会话三个真发现，全部来自"**先建基线**"这个动作，而不是来自"写新功能"：
>
> | 动作 | 意外发现 |
> | :--- | :--- |
> | 修 2 个预存在红测试 | 根因是「种子按 context 跑一次 + H2 全 JVM 共用」的顺序依赖，**不是测试写错** |
> | 给换电补原子性测试 | 注释声称"同事务双写"而全仓无 `@Transactional` —— **真数据错** |
> | 查 `enforced` 路径 | 我自己写的路径**根本不存在**（validate 却报 0 issue） |

**共同点：它们都不是"我打算找的问题"，是"验证时撞上的"。**

所以方针是：**下一个目标不要直接开功能，先建验收。** 验收过程本身会暴露问题，
而且暴露的是**已经存在的问题**（不是新引入的）—— 那类问题最有价值，
因为它们已经在生产里潜伏了很久。

## 五、如果还是要派集群：一条可执行的判据

**除了前端，当前没有可派的切片。** 而前端没基线 → **不该派双路**。

所以「继续派集群」这个指令在当前状态下**没有合法的落点** ——
正确的下一步是**主进程单干：给前端建验收**，做完再评估要不要派。

若确实要派，用这条判据（本会话实测有效）：

> **先问：这一波的两路，会不会改同一个方法体？**
> 不会（各改自己独立的一行）→ 可以派，父收口冲突（wave42 实测 2 分钟）
> 会 → 不许派，改成串行或换切片

## 六、一句话

**JPA 线的矿挖完了。下一个真压力在前端，而前端缺基线。**
**所以下一步不是"派集群"，是"建验收" —— 而建验收的过程本身会压出问题。**

这个结论如果成立，它本身就是一条 KB 产出：
**「验证活动对新知识的贡献 ≥ 开发活动」** ——
本会话 3 个真发现全部来自验证，0 个来自开发。

## 七、把它推到底：**仪器，而不是政策**

上面那条观察在 `borrowing-from-model-arch.md` 里被推到了更硬的形式，
并且**已经找到并处理了一个反例**：

| 状态 | 结果 | 证据 |
| :--- | :--- | :--- |
| **无仪器** | 从未执行 | `引用计数`、代谢配额、时间修剪规则 |
| **有仪器、未接线** | **也未执行** | `check-freshness` 写了 2 天没跑，一跑抓出 2/3 仓烂 |
| **有仪器、已接线** | 执行，且立刻发现问题 | 接线当天就抓到 |

**所以接下来的每一个动作，先问：我是在写政策，还是在装仪器？**

- 写一条"应该多验证"的规则 → **政策**。多半不会被执行。
- 把某条验证**接进 `mvn test` / CI / pre-push** → **仪器**。它会自己亮。

本会话所有有效动作都是后者。**建议下一个 agent 沿用这个判据** ——
包括在决定"要不要把某条经验写进 KB"时：
**如果它答不出"接在哪根线上"，它现在不该入库。**

> 这条本身也还没入库 —— 按它自己的标准，它得先找到一个"接线点"。
> 而它可能的接线点是：`collab validate` 的一条规则，或 `pull-request` 模板里的一句话。
> **在那之前，它留在这里，不入库。**

## 八、**09-20 实测：L3 已停摆，而我建的仪器测错了东西**

> 09-19 之后又跑了一整天（wave58 → **wave169**）。回来核对，结论比上面几条都硬。

### 事实

| 指标 | 09-19 收官 | 09-20 21:09 |
| :--- | :--- | :--- |
| evolutionary 波次 | wave58 | **wave169**（+111） |
| 前端测试 | 35/35 | **185/185**（×5.3） |
| **新增拦截候选** | — | **0**（6 行全是 09-19 及以前，且全部已 harvest） |
| **collaboration HEAD** | `e293673` | **`e293673`（一动没动）** |

**111 波 L2，L3 零增量。**

### 三个读数，一个比一个不客气

**① L3 停滞不是纪律问题，是任务类型问题。**

09-20 的波次名全是 `CouponTemplateView` / `PackageOverrideView` /
`StationDetailView` / `TemplateView` —— **"View 化"是已确立模式的机械应用**。
机械应用**撞不到墙**，所以产不出拦截候选。

⇒ 09-19 写的「JPA 线的矿挖完了」**同样适用于 View 线**。
**换一条线继续跑，不等于换了压力。**

**② 政策里那条刹车，从没被接上。**

`patterns/pressure-routing` 明写：

> **L3：连续 5 tick `interceptions` 与条目 diff 均为 0 → 停**

**实际连续 111 波为 0，没停。** 这是 [[patterns/policy-without-mechanism]]
的教科书案例：判据存在、可观察（数一下就知道）、**但没有仪器去数**。

**③ 最不客气的一条：我建的仪器，测的是错误的失效模式。**

09-19 给候选池装了龄期检查（`collab memory`），假设是
"**候选会堆积、没人处理**"。实际是 —— **候选根本不产生**。

| | 我假设的失效 | 实际的失效 |
| :--- | :--- | :--- |
| 候选池 | 有候选，挂着没人 harvest | **没有候选**（6 行全是旧的） |
| 仪器表现 | 龄期超阈就报警 | **恒绿**（没东西可报） |

**所以那台仪器永远不会亮。它测的是一个不存在的病。**

> 09-19 写「没接线的仪器等于没装」—— 那条对。
> 但还有更坏的一档：**接了线、却是绿线的仪器**。
> 它比没有更危险，因为它**看起来像在监控**。

### 方针第四条：**先给"零增量"装线**

不是再写一条"应该多 harvest"，是把 ② 那条**已有判据接上**：

> **可执行形式**：`git -C collaboration log --oneline <上波 HEAD>..HEAD` 有无新 commit？
> 无 → 本波记 **L3 干涸**；连续 5 波干涸 → **停 wake，W4**，不要继续 View 化。

**成本**：一条命令。**而它不会像候选池龄期那样恒绿** ——
因为它测"**有没有产出**"，不是"有没有积压"。

**判据的教训（值得单记）**：

> 给"停滞"装仪器时，**要测"产出为 0"，不要测"积压 > 0"**。
> 积压只是**其中一种**停滞形态；"什么都不产生"是另一种，
> 更常见，也更容易被漏掉 —— 因为**它看起来像在正常工作**。
