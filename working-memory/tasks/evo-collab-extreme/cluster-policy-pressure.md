# 用 wave42 压集群策略：三条证据

**日期**：2026-09-19 ｜ **材料**：wave42 双路（46a AlertStore ∥ 46b MaintenanceTicket）

> 这是**一次真实的选择压力测试**，不是复盘感想。材料是 wave42 的实际执行记录
> 与 `patterns/extreme-unattended-cluster.md` 的对照。

## 证据 1：决定本波成败的那条规则，**政策里没有**

本波最重要的决定是「**先修基线再派集群**」——全量 205/2 红时不派工，
先修到 211/0（`3ceda84` 每个 context 独立 H2）。

理由不是洁癖：**红着基线派双路，新出来的红无法归因** —— 分不清是子代理写错了，
还是那两个旧红移动了位置。修完基线后 wave42 合并，217 = 211 + 3 + 3 算术对得上，
**零新红，可归因**。

```bash
grep -in "基线" patterns/extreme-unattended-cluster.md   # → 无
```

政策 163 行、22 条门禁，**没有一条讲"派工前基线必须绿"**。

## 证据 2：政策里最严的那条，**会禁止本波成功的做法**

`同路径写锁（v6）` 原文：

> 同一逻辑文件同时只允许 **一个** 写者（跨 worktree 亦禁语义双写）

而 wave42 的 46a 与 46b **都改了 `IotConfig.java`** —— 按字面 = 违规。
实际结果：两处改动是**各自删自己那行 import、各自替换自己那个 Bean**，
git 三方合并产生一处冲突，父进程 **2 分钟收口**，无 `<<<<<<<` 残留。

**判据错在哪**：它把两种东西压成一条禁令。

| | 定义 | 该不该禁 |
| :--- | :--- | :--- |
| **语义双写** | 两个写者改同一段逻辑（同一方法体、同一不变量） | **禁** —— 会互相覆盖 |
| **机械相邻行** | 两个写者各改自己独立的一行（相邻但无语义重叠） | **可放行** —— 父收口 |

政策只写了"同一逻辑文件"这个**位置**判据，没写**语义**判据。

## 证据 3：v8 的基础设施**真的承重**

本波实际用到、且**确实起了作用**的，全是 v8 加的那批：

| 机制 | 本波实际发生 |
| :--- | :--- |
| worktree 隔离 | 两个 worktree 独立写，主 checkout 零干扰 |
| 回执契约 | 两路都返回了结构化结果（文件清单 + 真实测试输出 + 是否碰共享行） |
| 派出会计 | N=2 派出，M=2 收回，**算术闭合** |

**v5–v7 的散文条文本波一条都没用上。**

## 结论

**不写 v10 散文。** 三条动作：

1. **补一条机制**：派工前基线必须绿（可观察：`mvn test` 退出码；
   强制动作：不派；执行面：已有）
2. **修一条判据**：同路径写锁拆成 语义双写（禁）/ 机械相邻行（可放行，父收口）
3. **压薄**：163 行里，v5–v7 的散文条文没有证据支持 —— 按 `pruning-policy`
   该降到 `dormant` 或合并，而不是再叠一层 v10

> 这次压测最有价值的发现是**证据 1**：
> 政策越来越长，却**漏掉了真正决定成败的那条**。
> 这与 `patterns/policy-without-mechanism` 同源，但更尖锐 ——
> 不只是"加了规则反而更慢"，而是**规则集本身跑偏了**：
> 条文在增长，覆盖面没增长。

## 证据 4：wave48 后父把「需判断」当成停机（2026-09-19 11:41）

集群**没有挂**。子代理 48a/48b 都回了；基线绿（13/13）；loop 里**已经列出**两条互不改同一方法体的下一刀（iot 工单 RSC ∥ station 接线）。

父却写「下一刀需判断」并问用户选 1 或 2，lanes 置 0。

这直接违反 `extreme-unattended-cluster` **收口≠停派（v7）**：

> 上波 ✅ 且仍有可并行项 → **同 tick 派出下一波**，不得等下一 wake

| 父当时的借口 | 实际该怎么做 |
| :--- | :--- |
| 文案「暂不可换」vs「不可换出」要产品拍板 | **父当场选一边**（对齐已有 UI「不可换出」）再派 |
| 不造未接线 view | 这是**选片过滤器**，不是停机条件 |
| 让用户选 1 或 2 | 「继续」= 可派；**暂停只听用户说暂停** |

**补一条可观察规则**（写进本任务 `loop.md`，不入库）：

> 基线绿 ∧ 存在两条互不改同一方法体的切片 ∧ 用户未说暂停 → **本 tick 必须派**。
> 「需判断」= 父选切片，≠ 停派、≠ 问用户。

## 证据 6：小切片 + worktree + Task = 负吞吐（2026-09-19 14:00–14:30）

本机实测：

| 动作 | 墙时间 | 结果 |
| :--- | :--- | :--- |
| `git worktree add`（~670 文件） | 30–70s | 常「failed」但树已建好 |
| Task 创建 bubble | 经常 Timeout | 子代理从未开工（53a、54a） |
| 父自己改 1–3 个文件并 commit | < 2 min | HEAD 前进 |

wave50–51 的切片（RSC 概览、¢→¥）用双 worktree 派工，**调度成本 ≫ 实现成本**。用户看到的就是「集群没在工作」。

另：未提交的共享内核抽取（`shared/money`）摊在工作区，父去答架构题 → HEAD 冻住，再次像停机。

**效率规则（本任务，不入库）**：

1. **预计父 5 分钟内写完 → 主树父写**，不建 worktree、不派 Task。
2. 双 worktree + 双 Task **只留给单路预计 >15 分钟**的切片（当年 JPA）。
3. 工作区有未提交业务改动 → **先 commit / 丢弃，禁止开下一波**。
4. 禁止再派 `toFixed` / 字段透传当 domain 切片；下一刀必须是**带名字的展示不变量**。
