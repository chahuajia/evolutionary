# 用 evolutionary 压 collaboration：方向与方针

**日期**：2026-09-19 ｜ **依据**：本会话全部实测（wave42、事务债、两次"找不到"、四次自纠）

---

## 一、当前处在哪：一个单调递减的矿

**JPA 化这条线走完了。** 全仓只剩 1 处 InMemory 注入，而它跨域、需先判断是否共享内核。

回头数这条线的产出：

| 波次 | 产出 | 对 KB 的选择压力 |
| :--- | :--- | :--- |
| wave41–42 + operator | 10 个域 JPA 化 | **≈ 0**（`pressure-routing` 说的"机械执行面根本不需要 KB"） |
| 事务债 | 1 个真 bug（数据错） | **1 条新 pattern** + 2 条拦截候选 |
| 种子时机 | 1 次"找不到" | 1 行 known-gap |

**规律很清楚：机械切片对 KB 零压力，设计墙才有。**

而"设计墙"的数量是**单调递减**的 —— 项目越成熟，撞墙越少。
JPA 线已经撞完（种子时机、事务边界两个都撞过了），再往前走是**重复同类切片**。

## 二、因此方针第一条：**不要为了压 KB 而造撞墙**

具体禁止：

- ❌ 不要为了"有产出"把已经做对的东西重构一遍
- ❌ 不要为了 harvest 而放大一个不存在的设计问题
- ❌ 不要在前端零测试的情况下开大改（那不是撞墙，是拆墙）

**判据**：如果我需要**编一个**设计问题才能 harvest，那这条压力线已经枯竭 —— 该停，而不是硬跑。
（这与 `pressure-routing` 的"L1 冒充 L3"是同一条，只是换了个伪装。）

## 三、方针第二条：**下一个有真压力的目标是前端**

理由不是"它是剩下的活"，是**它同时具备三个条件**：

| 条件 | 现状 |
| :--- | :--- |
| **有决策没落地** | `topic/fe-ddd-rsc` 的决策表 2026-09-17 就写了（RSC / 服务端读模型 / BC 视图模型），仍标「待实施」 |
| **有 KB 依据** | `patterns/frontend-ddd-rsc` 条目在，且账本里有它拦过一次的记录 |
| **会撞新墙** | 前后端边界、RSC 的序列化边界、服务端状态 vs UI 瞬态 —— **和 JPA 线完全不同类的墙** |

**但它的前置条件没满足：前端零测试 = 没有基线。**

所以顺序是：

```
1. 先给前端建一条能跑的验收（哪怕只有 next build + 一条冒烟）
2. 再按决策表改造，每步有基线可验
3. 改造中撞到的墙 → 才是真的 L2→L3 压力
```

**跳过第 1 步就是重演"红着基线派双路"** —— 那正是本会话花了大力气修掉的坑
（`3ceda84` 每个 context 独立 H2）。

## 四、方针第三条：把"找基线"本身当压力源

这是本会话最有价值的一条副产品，**它值得被压出来第二次**：

> 本会话三个真发现，全部来自"**先建基线**"这个动作，而不是来自"写新功能"：
>
> | 动作 | 意外发现 |
> | :--- | :--- |
> | 修 2 个预存在红测试 | 根因是「种子按 context 跑一次 + H2 全 JVM 共用」的顺序依赖，**不是测试写错** |
> | 给换电补原子性测试 | 注释声称"同事务双写"而全仓无 `@Transactional` —— **真数据错** |
> | 查 `enforced` 路径 | 我自己写的路径**根本不存在**（validate 却报 0 issue） |

**共同点：它们都不是"我打算找的问题"，是"验证时撞上的"。**

所以方针是：**下一个目标不要直接开功能，先建验收。** 验收过程本身会暴露问题，
而且暴露的是**已经存在的问题**（不是新引入的）—— 那类问题最有价值，
因为它们已经在生产里潜伏了很久。

## 五、如果还是要派集群：一条可执行的判据

**除了前端，当前没有可派的切片。** 而前端没基线 → **不该派双路**。

所以「继续派集群」这个指令在当前状态下**没有合法的落点** ——
正确的下一步是**主进程单干：给前端建验收**，做完再评估要不要派。

若确实要派，用这条判据（本会话实测有效）：

> **先问：这一波的两路，会不会改同一个方法体？**
> 不会（各改自己独立的一行）→ 可以派，父收口冲突（wave42 实测 2 分钟）
> 会 → 不许派，改成串行或换切片

## 六、一句话

**JPA 线的矿挖完了。下一个真压力在前端，而前端缺基线。**
**所以下一步不是"派集群"，是"建验收" —— 而建验收的过程本身会压出问题。**

这个结论如果成立，它本身就是一条 KB 产出：
**「验证活动对新知识的贡献 ≥ 开发活动」** ——
本会话 3 个真发现全部来自验证，0 个来自开发。
